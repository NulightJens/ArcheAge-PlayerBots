# PlayerBots delivery audit — 2026-09-02

## Verdict

The project produced real source code, but the delivery system overstated that
work as product progress. The registered live runtime contains only the nearby
quest-intake source at `fb0a315c9579fb2e7e249e47b37efa07a9404c51`. The
corrected identity, signpost quest, and road-routing wave is at
`1a52e7b44fab76939d9409561bdfa4739f1425e6` and passed its source gates, but it
is not installed. The road-routing layer is additionally not connected to the
bot host, so it could not move a live bot even after installation.

The current M-005 one-zone population milestone is not accepted. The latest
runtime demonstrated nearby quest intake with retained high-level bots, not a
level-one Nuian bot completing the first five quests, not three autonomous
bots, and not world travel. “Source green” and “product done” were conflated.

## Roadmap position

The retained T-079 evidence is a useful historical proof that one bot could
complete three small autonomous XP iterations on an older source/runtime
combination. It does not accept the current combined system. M-005 was reached
in infrastructure breadth, not in present-tense player-visible behavior.

The project is therefore reset to the first current vertical slice: create one
level-one Nuian bot, then have it discover, accept, navigate, execute, report,
and chain five starter-area quests under native AAEmu authority while an active
client witnesses the behavior. Population and scale are downstream of that.

## Why the operating system failed

1. Task completion became the unit of progress instead of player-visible
   behavior. A `done` task could mean source-only, receipt-only, or live proof.
2. Deployment was deferred until after large source waves. The feedback loop
   discovered environment and gameplay failures hours after the code that
   caused them.
3. Separate preparation, worker, integration, failure-receipt, and verification
   tasks multiplied handoffs without advancing a bot.
4. The client was treated as a final optional smoke rather than a continuous
   acceptance oracle for movement, interaction, combat, equipment, and packets.
5. Contracts optimized measurable process details such as expected test counts
   while the executable player scenario remained blocked.
6. Twenty-two isolated worktrees made the authoritative source/runtime pairing
   hard to see. The installed source trailed the reported integrated source.
7. Documentation and ledgers disagreed: README/roadmap limits, BOARD status,
   individual task status, installed source, and runtime behavior described
   different realities.
8. T-123's outcome was named “world navigation” although its delivered scope
   ended at a callable routing session. No production owner used it.

## AzerothCore Playerbots comparison

The reference project describes player-like bots, autonomous random world
population, quests, raids/battlegrounds, configuration, and large bot counts in
its [official README](https://github.com/mod-playerbots/mod-playerbots). Its
[runtime configuration](https://github.com/mod-playerbots/mod-playerbots/blob/master/conf/playerbots.conf.dist)
distinguishes random bots, quick party bots, and player-owned alt bots, and puts
population, questing, activity, travel, PvP, gear, professions, and performance
under one running system. `RandomPlayerbotMgr` continuously manages bot counts,
login/update rotation, activity, queues, and runtime statistics in the
[server loop](https://github.com/mod-playerbots/mod-playerbots/blob/master/src/Bot/RandomPlayerbotMgr.cpp).

Its AI is decomposed into strategies, triggers, prioritized actions, values,
prerequisites, alternatives, and continuations in
[`Strategy.h`](https://github.com/mod-playerbots/mod-playerbots/blob/master/src/Bot/Engine/Strategy/Strategy.h)
and
[`Engine.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/master/src/Bot/Engine/Engine.cpp).
Quest, grind, RPG, exploration, and other destinations feed one travel-target
selection path in
[`ChooseTravelTargetAction.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/master/src/Ai/Base/Actions/ChooseTravelTargetAction.cpp).

The lesson is not to port WoW code or copy every subsystem now. The lesson is
to build a thin, continuously running vertical loop where population ownership,
goal selection, travel, local execution, recovery, and observation are wired
together. ArcheAge then extends that loop with trade packs, labor/professions,
ships, housing, factions, territory, and open-world PvP.

## Decision

`ops/DELIVERY-MODEL-V2.md` and `ops/GOALS.yaml` supersede task volume as the
measure of progress. Historical tasks and evidence remain retained. No feature
may be called complete until one fingerprinted candidate passes source gates,
is installed, produces native server state, is witnessed by an active client,
and repeats from a clean graceful restart where the goal requires persistence.
